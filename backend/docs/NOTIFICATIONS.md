# Notifications (Phase 9)

In-app notifications, persisted in PostgreSQL and delivered over REST and
Socket.IO, generated by domain events across Phases 4–8.

Specification: `BACKEND_PRD.md` §14, `BACKEND_TRD.md` §19, §22,
`BACKEND_ARCHITECTURE.md` §14, §16. Phase order from §38.

**No schema change was required.** `Notification` and `NotificationPreference`
were already present from Phase 2, with all three indexes this module needs.
Migration count remains **2**.

---

## Architecture

`ARCHITECTURE` §16 gives the pipeline; this is what it became:

```
follows / posts / projects / communities / messages
        ↓  (domain service raises an event)
   NotificationPort.emit()          ← the seam, unchanged since Phase 4
        ↓
   notifications.service.createNotification()
        ↓  suppression: self → block → preference → collapse
   notifications.repository            ← the only Prisma caller
        ↓
      PostgreSQL
        ↓  (persisted; only now)
   notification.socket.emitNotificationNew()
        ↓
   user:{recipientId} room
```

`TRD` §22 requires the notification service to _"remain independent of
individual controllers"_. It is: the dependency runs **one way**. Domain
services import `NotificationPort`; the port's live implementation imports the
notifications module; nothing in the notifications module imports a domain
service back.

### The port swap

The Phase 4 seam promised: _"Phase 9 replaces `noopNotificationPort` with a real
implementation… Nothing in this file's consumers changes when it does."_

**That promise was kept.** Not one of the seven existing call sites in
`follows`, `posts`, and `projects` was touched to activate delivery. Only the
binding at the bottom of `notification.port.ts` changed:

```ts
export const notificationPort: NotificationPort = liveNotificationPort;
```

`noopNotificationPort` is retained rather than deleted — it is the honest way to
disable notifications in an environment with no use for them, and it documents
what the seam looked like before it went live.

## REST API

All routes are under `/api/v1/notifications` and **all require
authentication**. A notification list is a digest of everything one person has
received; like messaging and unlike projects, posts, or communities, it has no
public face and therefore no `optionalAuth` route.

| Method | Path        | Purpose                                                          |
| ------ | ----------- | ---------------------------------------------------------------- |
| GET    | `/`         | The caller's notifications, cursor-paginated, with `unreadCount` |
| GET    | `/unread`   | Unread count alone                                               |
| POST   | `/read-all` | Mark every notification read                                     |
| POST   | `/:id/read` | Mark one read                                                    |

**There is deliberately no `POST /` and no `DELETE`.** Notifications are
server-generated in response to domain events — a create endpoint would be a
way to write arbitrary text into another user's panel — and no specification,
PRD line, or frontend affordance asks for deletion. The shipped panel offers
"mark all as read" and nothing else.

`GET /` returns `unreadCount` alongside the page because the panel renders both
and would otherwise need a second request on every open.

## Socket events

**One event, server-to-client only.**

| Event              | Payload                                                         |
| ------------------ | --------------------------------------------------------------- |
| `notification:new` | `{ notification }` — the full projected row, for **every** type |

**One payload shape, always.** `notification` is the same `NotificationView`
that `GET /notifications` returns, and it is never null. A client must never
have to branch on which server-side write path produced a row: batching is a
write-path concern and has no business being visible in the socket contract.

Routed to `user:{recipientId}`, the room every socket joins at connect from its
_verified_ handshake identity. The recipient id is read off the **persisted
row**, which the service resolved from a domain event, so no client names a
recipient at any point in the chain. Those two facts together make cross-user
leakage structurally impossible rather than merely unlikely.

**No inbound events.** Marking read is a REST call. A socket path for it would
be a second entry point into the same mutation, and a second place for the
ownership check to be missing. Phase 8 made the opposite trade for messaging
because sending a message is latency-sensitive; marking a notification read is
not.

**The fan-out is not an exception.** An earlier cut of this phase emitted
`{ notification: null, type, entityType, entityId }` for `project_update`,
because `createMany` returns no rows and re-reading up to five hundred of them
purely to put on a socket would have undone the batching. That was **rejected in
review** as a second contract on one event. The fix was to change the write, not
the wire: `createManyAndReturn` hands back the rows it inserted, under the same
`notificationSelect` every other read uses, so the fan-out costs no extra round
trip and the 500/100 bound below is untouched.

Delivery is a loop of one emit per recipient, not a room broadcast. There is no
room meaning "the followers of this project", and inventing one would put a set
of users behind a shared channel where a membership bug leaks one person's
notification to another. Every notification enters `user:{its own userId}` and
no other room.

## Suppression: four rules, in order

The order is a security decision and is asserted in the tests, not merely
commented.

| #   | Rule                           | Why                                                                                                                                                                                                            |
| --- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Self**                       | You are never notified about your own action. Costs no query.                                                                                                                                                  |
| 2   | **Blocking, either direction** | Consistent with Phases 4–8, where a block outranks membership, ownership, and admin role. Without it, blocking someone would still let them put text in front of you every time they liked something of yours. |
| 3   | **`inApp` preference**         | `false` means the row is **never written**, not merely hidden on read. A stored-but-invisible notification is still a record of activity the user asked not to be told about.                                  |
| 4   | **Collapse**                   | See below.                                                                                                                                                                                                     |

Self and blocking come before the preference lookup so the common refusals cost
no query, and before collapse so a suppressed event never reads history it has
no business reading.

A suppressed notification produces **no socket traffic either** — otherwise
muting a type in settings would still make a badge flicker.

### Preferences

`NotificationPreference` and its endpoints already existed from Phase 4. This
phase **consumes** them and adds nothing: `GET/PATCH
/users/me/notification-preferences` are unchanged.

A user with no preference row defaults to `inApp: true`, matching the schema
default and `users.service.getNotificationPreferences`. Treating the absence as
"off" would silently mute the feature for most of the user base, and would
disagree with what the settings screen shows them.

## Deduplication: collapse while unread

**The specification is silent on deduplication.** No PRD, TRD, or ARCHITECTURE
line addresses it, and the schema carries no unique constraint that could
arbitrate one. This is therefore a deliberate product decision — proposed during
implementation and **ratified as an explicit Phase 9 design decision** — stated
here rather than buried in a query.

> **The rule:** an identical notification (same recipient, type, actor, and
> target) is suppressed **if the previous one has not been read yet**. Once the
> recipient has read it, the next occurrence is genuinely new information and
> gets its own row.

Why this shape and not a time window:

- **No tuning constant.** "Five minutes" would be arbitrary, and wrong for both
  a rapid like/unlike/like and a conversation that goes quiet for an hour.
- **Self-limiting where it matters.** Twenty messages in one conversation
  collapse to one unread badge entry; open the thread and the next message
  notifies again.
- **Explainable in one sentence,** which a decay window is not.

**Not collapsed:** `project_invite`, `community_invite`, `invite`,
`project_update`. Each invitation is a distinct act and each update is distinct
content — collapsing them would lose information rather than reduce noise.

**Known limit, explicitly accepted:** two _simultaneous_ identical events can
both pass the check, because no unique index exists to arbitrate and adding one
would be a schema change this phase may not make. The outcome is one redundant
row — a cosmetic defect, not a correctness or security one, and it is **accepted
as a documented Phase 9 limitation** rather than worked around.

Not worked around, deliberately: the arbiter would be either a unique index
(a schema change, forbidden this phase) or an advisory lock on every
notification write. Phase 8 uses `pg_advisory_xact_lock` for conversation
creation, where the cost buys correctness; paying it on the hottest write path
in the system to avoid an occasional duplicate row is the wrong trade.

## Notification types and triggers

| Type               | Trigger                         | Since                                               |
| ------------------ | ------------------------------- | --------------------------------------------------- |
| `follower`         | `follows.service`               | Phase 4 seam, activated                             |
| `like`             | post like, project like         | Phase 5/6 seams, activated                          |
| `comment`          | comment on a post               | Phase 6 seam, activated                             |
| `reply`            | reply to a comment              | Phase 6 seam, activated                             |
| `mention`          | `@handle` in a post or comment  | Phase 6 seam, activated                             |
| `project_invite`   | added to a project              | Phase 5 seam, activated                             |
| `community_invite` | added to a community            | **new in Phase 9**                                  |
| `message`          | direct message sent             | **new in Phase 9**                                  |
| `project_update`   | project update posted (fan-out) | **new in Phase 9**                                  |
| `invite`           | —                               | no trigger; the two specific members above are used |
| `achievement`      | —                               | **Phase 10** — no awarding engine exists            |
| `moderation`       | —                               | **Phase 11** — no moderation actions exist          |

`PortNotificationType` remains a **subset** of the schema's twelve members:
`achievement` and `moderation` are absent so no caller can raise them before
there is anything to raise them for, and `invite` is absent because
`NotificationPreference` is keyed by type — a user muting one kind of
invitation should not silently mute both.

> **Integration concern — frontend union mismatch.** The shipped frontend's
> `Notification["type"]` union carries the generic `invite` member and not
> `project_invite` / `community_invite`. The backend emits the **specific**
> members — ratified — so the two preference toggles stay independent. The
> frontend union therefore has to widen to accept them, or map both onto its
> existing `invite` branch for display. No backend change is pending for this;
> it is recorded here so the frontend phase does not discover it by surprise.
> Nothing else in the projection differs — every other key the frontend's
> `Notification` and `NotificationWithActor` declare is present.

### Community invitations

Being _added_ by someone else notifies. **Joining under your own steam does
not** — `resolveJoin` is a different code path, and you already know you joined.

### Message notifications

One notification per recipient, keyed on the **conversation**, not the message.
Combined with the collapse rule, that is what stops a chat becoming a
notification firehose: a burst of twenty messages collapses to one unread entry,
and opening the thread lets the next message notify again. **Ratified** as the
intended behaviour rather than tolerated as an artefact of the collapse rule.

### The `project_update` fan-out

Phase 5 deliberately emitted nothing here, on the grounds that the port is
single-recipient and looping over followers inside the projects service would
put delivery fan-out in the domain layer. **That reasoning still holds** — the
projects service now calls a _notifications_ helper rather than looping, so the
domain says "this happened, to these followers" and the notifications module
owns batching, suppression, and delivery.

Bounded three ways, because it runs **inline**: no queue library is installed
and this phase adds no dependencies. The two constants are **ratified Phase 9
safety limits**, not tuning knobs to be raised casually.

- The follower query itself takes at most `FANOUT_MAX_RECIPIENTS` (**500**).
- Suppression resolves in **batched** queries — one block lookup and one
  duplicate lookup per batch of `FANOUT_BATCH_SIZE` (**100**) — never one per
  recipient.
- Rows are written with `createManyAndReturn`, one statement per batch, which
  both writes the batch and yields the projections the socket emit needs.

Beyond the ceiling, remaining followers are simply not notified in-app; they
still see the update on the project itself, which is where project updates are
read. Raising the ceiling is a later conversation about a real queue.

## Authorization

`loadOwnNotification` is the single gate for every notification-scoped
operation, and it always throws **404, never 403**. A 403 would confirm that a
notification with that id exists and belongs to somebody — exactly the
confirmation an enumeration attack wants.

**The recipient is structural, not checked.** No route, schema, or service
function has a parameter for whose notifications to read or mutate; every one
resolves the caller from the verified access token. That is a stronger
guarantee than a check, because there is no branch to get wrong.

**Platform admin has no special power here.** An admin cannot read another
user's notification list — that list is a digest of everything they have
received. Phases 4–8 kept admin out of ordinary social surfaces, and this is a
more sensitive surface than any of them.

**Never trusted:** `userId`, `recipientId`, `actorId`, `type`, `message`,
`isRead`, `readAt`. None appears in any schema, so Zod strips them and they
never reach a service.

## Read state

`isRead` + `readAt` on the row, with `[userId, isRead]` backing the badge count.

Marking read is **idempotent in SQL**: the `where` clause carries
`isRead: false`, so a second call matches nothing and the original `readAt`
survives. Re-stamping it would rewrite history to say the user read it later
than they did.

`markedRead: 0` from `/read-all` is a **success** — the caller asked for a state
that already held — not a miss.

Unread counts are one indexed `COUNT`. No notifications are loaded.

---

## Pagination

Cursor, per TRD §14's preference for high-volume and real-time collections — a
notification list is both. `createdAt DESC` with `id DESC` as the tiebreak, so
paging stays stable when several notifications land in the same millisecond,
which a fan-out makes routine rather than rare. Reuses `utils/pagination.ts`.

---

## Message text

`Notification.message` is a stored string, rendered at write time. The schema
says why: _"Rendered at write time so the list needs no per-row joins to
display."_

The consequence, stated plainly: **the text is a snapshot.** An actor who later
changes their display name does not rewrite past notifications. That is correct
for a timeline of past events, but it is a consequence of the schema's design
rather than an independent choice.

`renderNotificationMessage` is an exhaustive `switch` with no `default`. A
thirteenth enum member would fail to compile rather than render as empty text in
everyone's panel.

## Redis

**None used.** Nothing notification-specific needs it. The Socket.IO Redis
adapter remains conditional on horizontal scaling (§14), and presence is Phase
8's.

## Background jobs

**None added.** TRD §25 makes job infrastructure optional (_"may be used"_) and
ARCHITECTURE lists notification fan-out as an _example_ of a job. §16's own
pipeline is synchronous, `bullmq` is not installed, and this phase adds no
dependencies — so the fan-out runs inline and is bounded instead.

## Fixed in this phase

**The `project_update` socket payload was unified with every other type.** See
_Socket events_ above: the fan-out briefly emitted a second frame shape because
`createMany` returns no rows. `createManyAndReturn` removed the reason for it
without relaxing the 500/100 fan-out bound.

**The Phase 5 `project_invite` emit passed no `subject`,** so the rendered
message read _"Ada added you to the project."_ — grammatical, and missing the
only fact that mattered. The call site in `projects/members.service.ts` now
passes `subject: context.row.title`. Regression: the integration test anchors
on `/added you to the project Beacon Relay.$/` rather than a substring, so
dropping the subject again fails loudly.

**`announceMentions` hardcoded `entityType: "post"`** while
`comments.service.ts` passed a _comment_ id. A mention inside a comment was
therefore recorded as pointing at a post that does not exist.

The defect was invisible while the port was a no-op, because nothing persisted
the mismatch; activating delivery turns it into a notification that deep-links
nowhere. `entityType` is now a parameter defaulting to `"post"`, so the two post
call sites read unchanged, and the two comment call sites pass `"comment"`.
Regression test: _"notifies on a mention in a comment, targeting the COMMENT"_.
